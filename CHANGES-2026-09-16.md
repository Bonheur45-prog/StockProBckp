# StockPro — Fix session, 2026-09-16

Three bugs patched this session, in the order fixed. Each entry: what was
wrong, what changed, and how to test it. Verification here was static
(tests, lint, build, boot-test against a dead Mongo URI, standalone
edge-case scripts) — none of it exercised a live MongoDB, so a real
sync/checkout pass on your side is still the closing step for all three.

## 1. Sale stock decrement applied twice (fixed)

**The bug.** `createSale()` on the client wrote two local records for one
sale — a decremented `product` and a separate `StockMovement(type="sale")`
— and queued both as dirty. Sync pushed both in the same request; the
server processed the `sales` array and the `stockMovements` array
independently, decrementing stock twice for the same sale. This wasn't an
edge case: the client has no direct-online path (`POST /api/sales` is
never called by the UI), so every sale, online or offline, went through
this double decrement.

**The fix.** `client/src/lib/repo.js` — `createSale()` no longer queues a
`StockMovement` for its own line items. It still optimistically decrements
`product.quantityOnHand` locally for instant UI feedback and still queues
the `Sale` itself. The server's `performSaleCreation()` is now the sole
place that decrements stock and writes the authoritative `StockMovement`
(with `relatedSaleId`) for a sale — that record reaches the device on the
next pull.

**Known trade-off.** A sale made offline won't show in the Stock page's
movement log until it has synced and the next pull brings the server's
record down. The product's on-hand quantity is unaffected — nothing else
in the client reads `stockMovements` to compute current quantity.

**How to test.**
- `cd client && npx vitest run src/lib/__tests__/createSale.test.js` — 5
  regression tests: exact single decrement, no local movement queued for a
  sale, correct sale totals, insufficient-stock still rejected, two
  sequential sales don't drift.
- Manual (needs live Mongo): note a product's starting quantity, sell N of
  it, sync, confirm the server's quantity is `starting − N`, not
  `starting − 2N`.

## 2. Sync push bypassed every role restriction (fixed)

**The bug.** The direct REST routes restrict catalog/inventory writes to
owner/manager (`requireRole("owner", "manager")` on product, stock,
supplier, and purchase-order routes). `POST /api/sync/push` had no such
check — any authenticated cashier could push a product edit, stock
adjustment, supplier change, or purchase order straight through sync and
it would apply, completely bypassing the restriction enforced everywhere
else.

**The fix.** `server/src/controllers/syncController.js` — `push()` now
gates each category to match its direct-route equivalent: products,
stockMovements, suppliers, purchaseOrders, and poReceipts require
owner/manager; sales and creditPayments stay open to any role (cashiers
legitimately create both through the direct routes too). A blocked item is
rejected into `results.errors` with a 403-style message rather than
failing the whole push — one blocked product edit doesn't take down an
otherwise-legitimate batch of the same user's own sales in the same
request.

**How to test.**
- `node verify_push_role_gate.mjs` (included at the repo root) — traces
  the exact control flow with a mixed batch (one of everything) as both a
  cashier and an owner; confirms a cashier's product/movement/supplier
  entries land in `results.errors` with zero DB calls attempted, their
  sale still succeeds, and an owner sees nothing blocked.
- Manual (needs live Mongo): log in as a cashier, force a product-edit
  payload into a `/sync/push` request (bypassing the UI), confirm it comes
  back in `errors` and the product is unchanged in the database.

## 3. Sale price/discount had no server-side validation (fixed)

**The bug, two parts.**
- Any client could submit an arbitrary `unitPrice` for a catalog line item
  and the server accepted it verbatim — no check that only owner/manager
  can negotiate a price different from the catalog `sellPrice`.
- `discount` was only ever floored to keep `total` at a minimum of 0; a
  discount larger than the subtotal, a negative discount, or a
  non-finite/garbage value (`Infinity`, a non-numeric string) all passed
  through silently instead of being rejected.

**The fix.** `server/src/controllers/saleController.js` —
`performSaleCreation()` now takes a `userRole` parameter (threaded through
from both `createSale()` and `push()`). A catalog line item with a
`unitPrice` differing from the product's `sellPrice` is rejected with 403
if the caller is a cashier; owner/manager keep unrestricted override
(negotiating price is a real feature). Every `unitPrice` — catalog
override or custom line — and the `discount` itself are validated as
finite, non-negative numbers, and the sale is rejected outright if
`discount > subtotal`, rather than silently clamping the total to 0.

`client/src/pages/POS/POS.jsx` — the price-edit control in the cart is now
hidden for cashiers (mirrors the existing `canVoid` pattern for void), so
a cashier gets immediate UI feedback instead of a confusing server
rejection after checkout. The server validation above is the actual
enforcement; this is UX only.

**How to test.**
- `node verify_sale_validation.mjs` (included at the repo root) — 18
  isolated edge-case assertions against the exact validation logic: valid
  discounts, negative/NaN/Infinity discounts rejected, a cashier's
  no-op price (equal to catalog) allowed, a cashier's actual override
  rejected, owner/manager overrides allowed, negative/non-finite override
  prices rejected regardless of role, discount-equal-to-subtotal allowed,
  discount-over-subtotal rejected.
- Manual (needs live Mongo): as a cashier, try to check out with a
  negotiated price — button should be hidden; force the payload anyway —
  server should reject with 403. Try a discount larger than the cart
  subtotal — should be rejected, not silently capped.

## Also found, not yet fixed

While tracing bug #1's pattern (client queues a redundant local mutation
alongside the "real" one), the same shape turned up in PO receiving
(`repo.js:receivePurchaseOrder`) — but with the opposite failure mode.
There, the queued `StockMovement` and the `poReceipts` entry deliberately
share a `clientId` so `applyStockMovement`'s idempotency check treats the
second as a no-op — that part is correct on purpose. But
`performReceivePurchaseOrder`'s `if (alreadyApplied) continue;` fires
*before* `line.quantityReceived += applied`, so stock is correctly
incremented once, but the PO's own `quantityReceived`/status never
updates. Every PO received through the app shows the right stock bump but
a PO stuck at 0 received. Not part of this session's scope — flagging for
whenever it's prioritized.
