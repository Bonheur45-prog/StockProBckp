# StockPro — Fix session, 2026-09-17

## 1. UI-level gating for Products and Stock pages

**The gap.** Suppliers and Purchase Orders were already nav-gated to
owner/manager (`roles: ["owner", "manager"]` in Layout.jsx) — a cashier
can't reach them at all. Products and Stock had zero gating: a cashier
could open either page, attempt to create/edit/delete a product, import a
CSV, restock, or adjust stock — all of which the server now correctly
rejects (since the Bug #1 sync-push role gate), but the client let them
try and the attempt just sat there permanently failing.

**The fix.** `client/src/pages/Products/Products.jsx` and
`client/src/pages/Stock/Stock.jsx` — added a `canManageCatalog` check
(`role === "owner" || role === "manager"`, same naming as the server-side
gate for consistency). Mutating buttons (Add product, Import CSV, per-row
Edit/Delete, Adjust, Restock) are hidden for cashiers; both pages remain
fully viewable (a cashier still needs to look up prices and stock levels).
Defense-in-depth: the underlying functions (`openCreate`, `openEdit`,
`handleDelete`, `handleImportFileSelected`, `openModal`, `handleSubmit`)
also refuse to proceed even if somehow triggered another way, not just the
buttons that call them.

## 2. Critical: every cashier sale was silently role-blocking its own product, forever

**Found while designing the feature below** — tracing "what happens to a
cashier's product entry after a normal sale" surfaced this before it
could poison the stuck-records list with false positives.

**The bug.** `createSale()`, `restock`/`adjustStock`, and
`receivePurchaseOrder()` all unconditionally set `dirty: 1` on the product
they touch, as part of their optimistic local quantity update. The
server never reads `quantityOnHand` from a product push at all (already
excluded from that update, unrelated to this bug) — so this was always a
no-op for syncing the quantity. It became actively harmful once product
pushes were role-gated to owner/manager (Bug #1): a cashier's own,
completely ordinary sale marks their product dirty, that entry is
rejected by the role gate on every future push, forever — and a
permanently-dirty product also never receives any future catalog update
from pull again, since pull skips anything locally dirty. **Every cashier
sale, restock, or PO receipt ever made since Bug #1 landed would have
left that product silently frozen — no future name/price/etc. update ever
reaching that device again — with zero visible symptom.**

**The fix.** All three sites now write `dirty: product.dirty` (preserve
whatever the product's existing dirty state already was) instead of
forcing `dirty: 1`. A product with a genuine pending edit stays dirty and
still syncs correctly; a product touched only by a quantity change is
never marked dirty for that reason, and its true quantity is restored (if
it ever drifts) by the next ordinary pull — the same reconciliation path
that already runs on every sync, not a new mechanism.

**Verified:** added "does not mark the product dirty" + "preserves an
existing genuine pending edit" tests to `createSale.test.js`,
`receivePurchaseOrder.test.js`, and a new `restockAdjust.test.js`.
Validated by reintroducing `dirty: 1` at all three sites — confirmed the
exact 4 tests fail — restored the fix — confirmed 40/40 pass.

## 3. Stuck-sync-record recovery ("Couldn't sync" screen)

**The problem this closes.** A record the server permanently rejects
(role changed mid-flight, a discount that somehow still fails validation,
etc.) stays `dirty: 1` forever — the 30-second retry loop keeps resending
the same doomed payload indefinitely, and until now there was no way to
see which records were actually stuck (vs. just not-yet-synced) or do
anything about the ones that were. Void doesn't help: a stuck record
never reached the server, so nothing to reverse exists there — it's a
local-only draft, not a shared transaction.

**Design decisions, and why:**
- **No role check on resolving a stuck record.** It never reached the
  server — no one else has seen it — so acting on your own device's own
  unsent draft is a different, lower-stakes thing than void (which
  reverses something already shared). Any authenticated user can discard
  or retry their own stuck records.
- **"Discard" never hand-computes a rollback.** A record with no server
  `id` (never synced) is deleted outright — nothing server-side to fall
  back to. A record that WAS synced before, now with a rejected edit on
  top (e.g. a role-blocked product update), is cleared of
  `dirty`/`syncError` and left in place, then a sync is triggered
  immediately — the next pull restores the server's true values through
  the exact reconciliation path that already runs on every successful
  sync, rather than new code trying to guess the correct rollback.
- **Sales get "Edit & Retry" in addition to Discard; everything else gets
  Discard only.** Sales are the concrete, understood failure case
  (discount/price validation, or a genuine multi-device stock race).
  Retry reopens the sale as an editable cart and resubmits through the
  exact same `createSale()` validation as any new sale — never a special
  "skip validation" shortcut. Quantities are NOT silently capped to
  current stock (unlike the existing "Repeat Sale" feature for completed
  sales) — the cashier needs to actually see a stock discrepancy and
  decide, not have it quietly resolved for them; the existing "Not enough
  stock for X (have Y)" checkout error already says exactly what's wrong
  if it comes to that.
- **The old stuck sale is discarded immediately when "Edit & Retry" is
  clicked, before the cart is even shown** — not after the retry
  succeeds. Waiting would leave a window where both the old sale's
  optimistic stock decrement and the new one's could be live on the
  device at once; the old one's product-side effect does self-heal on its
  own (via the fix in §2), but only once that sync actually completes,
  and there's no guarantee it has by the time the cashier finishes
  editing.

**What changed:**
- `client/src/lib/sync.js` — sync-push errors are now written onto the
  actual rejected record (`syncError` field) inside the existing reconcile
  transaction, not just kept in the transient in-memory `lastErrors`
  (which is gone on page reload). Added `listStuckRecords()` (every dirty
  record with a `syncError`, across all 7 syncable tables) and
  `discardStuckRecord(type, clientId)` (the delete-or-clear logic above).
- `client/src/pages/SyncIssues/SyncIssues.jsx` (+ `.module.css`) — new
  page listing every stuck record with its type, a short summary, the
  actual rejection reason, and Discard (all types) / Edit & Retry (sales
  only) actions.
- `client/src/App.jsx` — new route, `/app/sync-issues`, no role
  restriction, deliberately not in the main nav (reached via the badge).
- `client/src/components/SyncBadge/SyncBadge.jsx` — clicking the badge
  now opens the new page when there are actual errors, instead of blindly
  retrying; unchanged (still retries directly) when nothing's actually
  wrong, just pending.
- `client/src/pages/POS/POS.jsx` — new `handleReopenStuckSale()` (see
  design notes above) and a mount effect that consumes
  `location.state.reopenStuckSale` once (from the new page's "Edit &
  Retry" button) and clears it immediately after, so a refresh or
  navigating back doesn't silently reopen the same sale again.

**Verified:** new `syncIssues.test.js` — 8 tests against the real

## 4. Found by hands-on testing: the badge itself couldn't find its own entry point after a reload

**The bug.** `SyncBadge.jsx`'s error state was driven by
`getLastSyncErrors()` — a transient, in-memory array in `sync.js` that
resets to empty on every page load. `listStuckRecords()` (§3) was built
specifically so the recovery screen would survive a reload by reading the
*persisted* `syncError` field on each record instead — but the badge was
never updated to use it, so it kept reading the old transient source.
Net effect: after any reload (or just returning to the app later), a
genuinely stuck record would still exist in the database, but the badge
would show "N pending" (amber, "tap to sync now") instead of "N couldn't
sync" (red, tap to open the recovery screen) — until the next automatic
sync cycle happened to run and fail again. In that window, there was no
visible way to find the recovery screen at all short of typing the URL
directly, which is exactly what happened in testing.

**The fix.** The badge now polls `listStuckRecords()` the same way it
already polls `pendingChangeCount()` (every 4s, plus an immediate refresh
whenever a sync cycle finishes — so it also updates right away after a
Discard or a successful retry from the recovery page, not just on the
next poll tick), and uses that as the single source of truth for both the
error tone/text and the click-to-navigate behavior. `getLastSyncErrors()`
is unused now but left in place — not incorrect, just superseded.

**Verified:** lint clean, build clean, full suite 49/49 (unaffected —
this fix has no data-layer test coverage of its own, since it's pure UI
wiring; same structural gap as the rest of §3's UI layer, see the note
below).
